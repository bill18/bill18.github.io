QuantLib Extension

Introduction

QuantLib is a well-known open source quantitative library for finance with Python, Java, and R interfaces generated by SWIG. It is gradually being adopted by financial engineers and researchers worldwide. But the lack of documentation slows adoption. Two books exist — Implementing QuantLib by Luigi Ballabio and QuantLib Python Cookbook by Goutham Balaraman and Luigi Ballabio — yet many readers still find the learning curve steep. The objective of this project is to provide an accessible extension to QuantLib Python, built on years of industry experience.

All my extensions will be compatible with the existing interfaces.

Here’s the critical ones:

  • Make QuantLib Python functions accept both objects and symbols. For example, many quantitative libraries on Wall Street let developers use the string “Act/Act” to represent the Actual/Actual day count basis, while QuantLib requires an ActualActual object. This is inconvenient when building pricing and risk applications at scale.

  • Make QuantLib Python functions accept dates in YYYYMMDD integer format alongside native Date objects. This makes code cleaner and eliminates boilerplate date construction.

  • Create a centralized calendar manager that loads calendars from a central repository via HTTP, HTTPS, file protocol, or database access. A URL-based loader and loaders for SQLite and MySQL are provided. Users can create their own loaders for other databases (Oracle, MongoDB, etc.) using the Strategy pattern.

  • Create a centralized schedule manager that loads bond and swap schedules from a central repository via HTTP, HTTPS, file system, or database. Also uses the Strategy pattern for loader flexibility.

  • Extend all critical classes to make them accept both symbols and objects. Decorator pattern will be used.

  • Design a generic curve builder based on QuantLib Python.

I’ll explain the idea by starting with an example written in plain QuantLib Python, then show how it looks with the extension. After that, I’ll walk through the symbol matching extension, calendar manager, schedule manager, and curve builder in turn.

An Example

The following example was from http://gouthamanbalaraman.com/blog/quantlib-bond-modeling.html. There’s no technical or calculation problem in this example, but we can make it simpler.

import QuantLib as ql

todaysDate = ql.Date(15, 1, 2015)
ql.Settings.instance().evaluationDate = todaysDate
spotDates = [ql.Date(15, 1, 2015), ql.Date(15, 7, 2015), ql.Date(15, 1, 2016)]
spotRates = [0.0, 0.005, 0.007]
dayCount = ql.Thirty360()
calendar = ql.UnitedStates()
interpolation = ql.Linear()
compounding = ql.Compounded
compoundingFrequency = ql.Annual
spotCurve = ql.ZeroCurve(spotDates, spotRates, dayCount, calendar, interpolation,
                         compounding, compoundingFrequency)
spotCurveHandle = ql.YieldTermStructureHandle(spotCurve)

issueDate = ql.Date(15, 1, 2015)
maturityDate = ql.Date(15, 1, 2016)
tenor = ql.Period(ql.Semiannual)
calendar = ql.UnitedStates()
bussinessConvention = ql.Unadjusted
dateGeneration = ql.DateGeneration.Backward
monthEnd = False
schedule = ql.Schedule(issueDate, maturityDate, tenor, calendar, bussinessConvention,
                       bussinessConvention, dateGeneration, monthEnd)
# list(schedule)
print('--- schedule ---')
for dt in schedule:
    print(dt)
print('--- schedule ---')

# Now lets build the coupon
dayCount = ql.Thirty360()
couponRate = .06
coupons = [couponRate]

# Now lets construct the FixedRateBond
settlementDays = 0
faceValue = 100
fixedRateBond = ql.FixedRateBond(
    settlementDays, faceValue, schedule, coupons, dayCount)

# create a bond engine with the term structure as input;
# set the bond to use this bond engine
bondEngine = ql.DiscountingBondEngine(spotCurveHandle)
fixedRateBond.setPricingEngine(bondEngine)

# Finally the price
npv = fixedRateBond.NPV()

print(npv)

From the above example, the following should be done when we calculate NPV for a fixed rate bond:

  • create simple objects for calendar, day count convention, interpolation method, etc.

  • build a curve

  • generate schedule for the bond

  • create a bond

  • create a pricing engine

Many companies opt to build curves and store in a centralized repository to be shared by all applications and all researchers.

Similarly, many companies opt to store schedules in databases to avoid code changes when schedules need to be modified.

On the other hand, developers and researchers prefer passing symbols for day count conventions, rolling conventions, etc. Many applications are data driven, when we need to have a way to translate symbols to objects anyway. It will be convenient if the library understand both symbols and corresponding objects.

Most of the researchers and developers prefer the following form of code:

import ext.QuantLibClassExt as qlx
import ext.SimpleCurveManager as mgr

todaysDate = 20150115
dayCount = '30/360'
schedule = 'BD20160115'
coupons = [.06]
settlementDays = 0
faceValue = 100.0

# setEvalDate(todaysDate)
spotCurve = mgr.ZeroCurve(todaysDate, 'ZC001')

fixedRateBond = qlx.FixedRateBond(
    settlementDays, faceValue, schedule, coupons, dayCount,
    curve=spotCurve, engine='DiscountingBond')

npv = fixedRateBond.NPV()

print(npv)

How was the above achieved?

This is achieved through the QuantLib Python Extension, discussed in the following sections. The curve data lives in a JSON file named ZC001.json, and the schedule in BD20160115.json. (These could also reside in a database; JSON files are used here for clarity, with no external dependencies.)

Directory tree

The project organizes files as follows. Many subdirectories are optional — for example, if you fetch calendars and schedules from a web service or database, you can omit the calendars and schedules directories.

├───calendars
├───config
├───curves
│   └───input <curve marks>
├───db
├───docs
│   └─── <documentation>
├───examples
├───ext
│   └─── <python code>
└───schedules
    └─── <schedule files>
  • The schedules directory is only needed if schedules are file-based — omit it if using a database or web service.
  • The calendars directory follows the same rule.
  • The db directory is only needed for SQLite storage of calendars, schedules, and curve inputs.

The following sections assume file-based storage for simplicity.

Class and enum mapping

In practice, developers and researchers work with symbols: “Act/Act”, “Act/360”, “30/360” for day count bases, “TGT” for TARGET calendar, “NX” for NYSE, and so on. Applications are data-driven — almost no one hard-codes business conventions.

Since different firms use different symbols, and to make lookup case-insensitive, the symbol-to-object mapping is defined in a JSON file (QuantLibConfig.json under the config directory). This can also be stored in a database.

You can modify the configuration as needed, as long as keys are not duplicated. For example, business day rolling conventions are pre-defined as:

"ROLL_CONV_MAP" : {
	   "FOLLOWING"        : "Following",
	   "MODIFIEDFOLLOWING": "ModifiedFollowing",
	   "PRECEDING"        : "Preceding",
	   "MODIFIEDPRECEDING": "ModifiedPreceding",
	   "UNADJUSTED"       : "Unadjusted",
	   "HALFMONTHMODIFIEDFOLLOWING": "HalfMonthModifiedFollowing",
	   "F"   : "Following",
	   "MF"  : "ModifiedFollowing",
	   "P"   : "Preceding",
	   "MP"  : "ModifiedPreceding",
	   "U"   : "Unadjusted",
	   "HMMF": "HalfMonthModifiedFollowing"
	},

All keys are uppercase. Multiple keys can map to the same class — in the example above, both “FOLLOWING” and “F” resolve to the Following rolling convention. The mapper performs case-insensitive lookup by converting input to uppercase first.

Additional configuration details are available in the repository.

Class extensions

It would be convenient if functions that accept objects of specific classes could also accept symbols — for example, “Act/Act” for a day counter or an integer 20150115 for a date.

Design patterns — Decorator & Composite

The Decorator pattern describes a way to add or remove behavior dynamically. When decorating a class, it is used together with the Composite pattern. The callables used for composition are held independently by a Composer object.

The following is quoted from https://python-patterns.guide/gang-of-four/decorator-pattern/#implement-dynamic-wrapper

A very common approach to the Decorator Pattern in Python is the dynamic wrapper. Instead of trying to implement a method and property for every method and attribute on the wrapped object, a dynamic wrapper intercepts live attribute accesses as the program executes and responds by trying to access the same attribute on the wrapped object.

A dynamic wrapper implements the dunder methods getattr(), setattr(), and — if it really wants to be feature-complete — delattr() and responds to each of them by performing the equivalent operation on the wrapped object. Because getattr() is only invoked for attributes that are in fact missing on the wrapper, the wrapper is free to offer real implementations of any methods or properties it wants to intercept.

There are a few edge cases that prevent every attribute access from being handled with getattr(). For example, if the wrapped object is iterable, then the basic operation iter() will fail on the wrapper if the wrapper is not given a real iter() method of its own. Similarly, even if the wrapped object is an iterator, next() will fail unless the wrapper offers a real next(), because these two operations examine an object’s class for dunder methods instead of hitting the object directly with a getattr().

As a result of these special cases, a getattr-powered wrapper usually involves at least a half-dozen methods in addition to the methods you specifically want to specialize.

A sample decorator is as below:

class DynamicDecorator(object):
    def __init__(self, to_be_decorated):
        self._to_be_decorated = to_be_decorated


    def func01(self, *args, **kargs):
        # do you decoration here
        self._to_be_decorated.func01(*args, **kargs)


    def func02(self, *args, **kargs):
        # do you decoration here
        self._to_be_decorated.func02(*args, **kargs)

    ...

    def __iter__(self):
        return self.__dict__['_to_be_decorated'].__iter__()

    def __next__(self):
        return self.__dict__['_to_be_decorated'].__next__()

    def __getattr__(self, name):
        return getattr(self.__dict__['_to_be_decorated'], name)

    def __setattr__(self, name, value):
        # you can setattr for this or fo the following
        setattr(self..__dict__['_to_be_decorated'], name, value)

    def __delattr__(self, name):
        delattr(self.__dict__['_to_be_decorated'], name)

Calendar Manager

The Calendar Manager lets users choose between their own calendars or QuantLib’s built-in classes. QuantLib generates calendars programmatically, which makes applications less flexible — holidays change, and modifying code to reflect them risks introducing bugs. Moreover, most QuantLib users cannot easily modify and rebuild the SWIG-generated bindings. A dedicated calendar manager solves this: it remains compatible with all QuantLib functions while allowing users to load calendars from files, databases, or web services.

Another consideration is that different firms use different calendar symbols and IDs. The Calendar Manager lets each user define their own symbol-to-source mapping.

The mapping is defined in a file named Calendar.idx under the config folder, where each entry specifies a calendar code and its data source. For file-based storage:

Design patterns

Singleton pattern

Calendars and schedules are static data — there is no need to create new objects every time they are used. Object construction is costly in both time and memory. The Singleton pattern ensures only one instance of a given type exists. In Python, __getattr__ makes Singleton implementation simpler than in Java or C++.

A typical Singleton in Python looks like:

class SimpleSingleton:
    class __SimpleSingleton:
        def __init__(self, *args, **kargs):
            # do initialization here
            
        def method1(self, *args, **kargs):
            # define method1

        def method2(self, *args, **kargs):
            # define method2

    # declare class variable
    instance = None

    def __init__(self, *args, **kargs):
        if not SimpleSingleton.instance:
            SimpleSingleton.instance = SimpleSingleton.__SimpleSingleton(*args, **kargs)

    # deligate the attribute lookup method to the inner class
    def __getattr__(self, name):
        return getattr(self.instance, name)

Strategy pattern

A key design goal is letting users define their own data loaders. A URL-based loader (for HTTP, HTTPS, file protocols) and a SQLite loader are provided out of the box. Users can follow the same pattern to implement loaders for Oracle, MS SQL Server, MySQL, MongoDB, and others.

Schedule Manager

In practice, financial firms maintain bond and swap schedules in centralized repositories for several reasons:

  • Programmatically generated schedules are not always correct. While QuantLib provides powerful schedule generation functions, getting them right requires deep expertise.
  • Avoiding program changes when schedules are modified.
  • Centralized schedules can be shared across applications, ensuring consistency.

Design patterns

The Schedule Manager uses the same singleton and strategy patterns as the Calendar Manager.

The repository

Schedules can be fetched from the file system or from web services. The URL pattern is configured in ScheduleConfig.json:

{
	"URL":"C:\\QuantLibExt\\schedules\\{0}.json"
}

This configuration is ignored when databases are used.

Curve Builder


Building curves is not a simple task. Curves should be constructed once and stored in centralized repositories shared by all applications, rather than rebuilt independently.


Market data should be consolidated in the same repositories.


QuantLib Extension provides two modules for curve building: one for simple curves and another for curves built from multiple instruments.


Simple Curve Builder


We used SimpleCurveManager in the Introduction section. A sample curve mark file looks like:

import matplotlib.pyplot as plt
import datetime
from matplotlib.ticker import FuncFormatter
import ext.QuantLibClassExt as qlx
import ext.SimpleCurveManager as mgr

def plotCurve(lineType, dates, rates):
    pydt = [datetime.datetime(d.year(), d.month(), d.dayOfMonth())
            for d in dates]
    fig, ax = plt.subplots()
    fig.set_size_inches(10.5, 9.5)
    ax.yaxis.set_major_formatter(
        FuncFormatter(lambda r, pos: '{:.2%}'.format(r)))
    plt.subplots_adjust(bottom=0.2)
    l, = plt.plot(pydt, rates, lineType)
